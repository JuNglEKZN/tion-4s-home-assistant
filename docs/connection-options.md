# Способы подключения TION 4S к Home Assistant

Ниже приведено практическое сравнение трёх основных архитектур.

---

## 1. Прямой Bluetooth через HA-tion

```text
TION 4S → Bluetooth Home Assistant → TionAPI/HA-tion
```

### Плюсы

- не требуется дополнительное оборудование;
- простая установка через HACS;
- быстрое начало работы;
- облако TION не требуется.

### Минусы

- чувствительность к расстоянию и помехам;
- зависимость от Bluetooth-стека Home Assistant;
- возможная конкуренция с телефоном, MagicAir и другими клиентами;
- при слабом RSSI возможны обрывы.

### Когда выбирать

- Home Assistant расположен недалеко;
- RSSI лучше `−70 dBm`;
- нужна простая интеграция без вскрытия бризера.

---

## 2. Bluetooth через ESPHome Proxy

```text
TION 4S → BLE → ESP32 Bluetooth Proxy → Wi‑Fi/LAN → Home Assistant → HA-tion
```

### Плюсы

- ESP32 можно установить рядом с бризером;
- улучшается радиопокрытие;
- один Proxy может обслуживать несколько BLE-устройств;
- не требуется подключение к UART TION.

### Минусы

- дополнительное устройство и питание;
- Proxy должен поддерживать активные соединения;
- остаётся несколько программных звеньев;
- универсальный Proxy не всегда оптимален для постоянного активного клиента.

### Когда выбирать

- встроенный Bluetooth HA не добивает;
- рядом с TION можно разместить ESP32;
- Proxy нужен также для других BLE-устройств.

---

## 3. Специализированный ESPHome BLE-клиент

```text
TION 4S → BLE → ESP32 с esphome-tion → Home Assistant API/MQTT
```

### Плюсы

- BLE-клиент расположен рядом с TION;
- меньше зависимости от Bluetooth хоста Home Assistant;
- специализированная конфигурация и диагностика;
- удобно, если ESP32 выделена только под бризер.

### Минусы

- требуется прошивка и сопровождение ESPHome;
- обновления ESPHome могут влиять на BLE-клиент;
- по-прежнему используется радиоканал;
- требуется стабильное питание и Wi‑Fi ESP32.

### Когда выбирать

- прямой BLE нестабилен;
- уже планируется отдельная ESP32;
- нужен специализированный локальный контроллер.

---

## 4. ESPHome UART

```text
TION 4S → UART → ESP32 с esphome-tion → Home Assistant API/MQTT
```

### Плюсы

- нет зависимости от BLE RSSI;
- наиболее прямой и потенциально стабильный канал;
- подходит для постоянной интеграции;
- ESP32 можно питать от сервисного разъёма при корректной реализации.

### Минусы

- требуется физическое подключение;
- нужно учитывать распиновку и логические уровни;
- ошибка подключения может повредить оборудование;
- сложнее установка и обслуживание;
- рекомендации зависят от конкретной платы ESP32.

### Важное предупреждение

В обсуждениях сообщества отмечается, что сервисный UART TION использует особенности распиновки и уровней сигнала. Нельзя подключать произвольную ESP32 без проверки схемы, допустимых уровней и документации проекта `esphome-tion`.

### Когда выбирать

- требуется максимальная стабильность;
- Bluetooth объективно ненадёжен в месте установки;
- пользователь готов к аппаратной доработке;
- понятны риски и электрическая схема.

## Практический алгоритм выбора

```text
Начало
│
├─ Home Assistant рядом и RSSI лучше −70 dBm?
│  └─ Да → начать с HA-tion
│
├─ RSSI слабый, но можно поставить ESP32 рядом?
│  ├─ Нужны и другие BLE-устройства → Bluetooth Proxy
│  └─ ESP32 только для TION → ESPHome BLE
│
└─ BLE остаётся нестабильным и допустима аппаратная установка?
   └─ ESPHome UART
```

---

## Рекомендация для большинства пользователей

1. Начать с прямого `HA-tion`.
2. Измерить реальный RSSI и проверить стабильность несколько дней.
3. При слабом сигнале поставить ESPHome Bluetooth Proxy.
4. Если ESP32 выделяется только для TION, сравнить Proxy со специализированным `esphome-tion` BLE.
5. Переходить на UART только при осознанной необходимости.

---

## Исторический контекст сообщества

Из переписки 2022–2026 годов видно:

- ранние версии BLE-интеграций были чувствительны к изменениям ESPHome;
- пользователи успешно управляли несколькими бризерами через одну ESP32, но стабильность зависела от версии и сигнала;
- при наличии отдельной ESP32 рядом с TION участники часто предпочитали специализированную прошивку универсальному Proxy;
- UART развивался как решение для устранения радиоканала и уменьшения числа промежуточных звеньев.

Эти наблюдения полезны как ориентир, но окончательный выбор должен учитывать текущие версии проектов и конкретную установку.
